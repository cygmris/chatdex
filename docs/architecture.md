# chatdex 架构

单进程 Go 常驻服务。三条主线贯穿全部设计：**只读 + 只本机**、**一份索引三个消费端**、**早期就能用**。

```
~/.claude/projects/**.jsonl ─┐
~/.codex/sessions/**.jsonl  ─┴→ parser.Registry → index.Scanner → SQLite(FTS5)
                                                                      │
                                          ┌───────────────────────────┤
                                          ↓                           ↓
                                   search.Engine ←──────────── summary.Worker → llm.Client
                                    （唯一检索实现）                              (127.0.0.1)
                          ┌───────────────┼───────────────┐
                          ↓               ↓               ↓
                   dashboard :5021   httpapi :5022   mcpserver :5022/mcp
                          └──────→ chat.Agent ──→ mcpserver.Tools（同一份工具实现）
```

## 模块

| 包 | 职责 | 不做什么 |
|---|---|---|
| `internal/model` | 统一消息模型（`SessionMeta` / `Block`） | 不认识任何 JSONL 结构 |
| `internal/parser` | 两套格式各一个解析器 + 注入指令剥离 | 不认识 SQL |
| `internal/index` | 建库、写块、增量水位、摘要队列 | 不做检索 |
| `internal/search` | **全项目唯一的检索实现** + CJK 归一化 | 不认识 JSONL |
| `internal/llm` | 摘要与聊天共用的 LLM 抽象 + 回环强制校验 | 无 embedding（R8 门控） |
| `internal/summary` | 抽稀、分段、后台 worker | 不阻断索引与检索 |
| `internal/chat` | 多轮工具循环 + 预算 | **不实现检索**，转调 mcpserver.Tools |
| `internal/mcpserver` | MCP 端点 + 三个工具（唯一一份工具实现） | 不写 SQL |
| `internal/httpapi` | JSON API + SSE | 不写 SQL |
| `internal/config` | 配置读写 + 字段元信息 + `Live` 热生效 | 不认识 HTTP |
| `internal/dashboard` | `embed.FS` 静态资源（外壳 + 四套主题 + 六个视图） | 对**会话数据**只读；写入仅限 chatdex 自己的配置 |

## 关键决策与它们的代价

### 1. CJK 用「单字切分 + U+0001 分隔符」，不用 trigram

FTS5 的 `unicode61` 把一整串中文当成一个 token。两个方案在 71.3 MB 真实语料上实测：

| 方案 | 索引库 | 相对文本 | 建库耗时 |
|---|---|---|---|
| `tokenize='trigram'` | 313.2 MB | ×4.39 | 15 s |
| **`unicode61` + CJK 单字切分** | **142.9 MB** | **×2.00** | **3 s** |

选后者。分隔符用 `U+0001` 而非空格是为了**无损**：`Strip` 能逐字节还原原文，
于是索引与展示共用同一份正文，省掉一份 GB 级拷贝。

**索引侧与查询侧必须走同一个 `split()`**——归一化不一致是这个模式最常见的 bug，
`normalize_test.go` 用真实 FTS5 表守住这条。

### 2. 会话排序按「最佳块」而非命中数

实测事故：找一段 restic 对话时，命中最多的两个会话（2272 / 2154 次）都不是目标，
目标只命中 669 次。所以排序用 `MIN(bm25)`，命中数只展示、不参与排序。
`engine_test.go` 里有一条以此事故为 fixture 的回归测试。

### 3. `snippet()` 只对最终展示的那几行算

`bm25()` / `snippet()` 只能用在**直接查询 FTS 表**的语境里，一旦与 `blocks`/`sessions`
同处一个 SELECT（哪怕写成子查询被优化器展平）就会报
`unable to use function bm25 in the requested context`。解法是
`WITH f AS MATERIALIZED (...)` —— `MATERIALIZED` 这个词缺一不可。

更要紧的是**不能在那个 CTE 里算 snippet**：它要把正文从外部内容表取回来重新分词，
代价与全库命中数成正比。实测查「的」（92 864 块命中）：只取 rowid 37 ms、
加 bm25 99 ms、**再加 snippet 2.83 s**；而外层根本不读片段，`fillBest` 又对 20 个
会话各重跑一遍——21 × 2.8 s，正好是修复前那 63.8 秒。

现在片段只按 rowid 单取（`MATCH ? AND rowid = ?`，<1 ms，与命中总数无关）。

### 4. 两个 listener 共用一个 mux

需求把 `5021` 定为前端、`5022` 定为 API+MCP。当两个独立服务写就会跨源；
同进程共享 `ServeMux` 则页面同源，不需要 CORS 也不必反代。

⚠️ Go 1.22 的 `ServeMux` 在**注册期**就对冲突模式 panic：`"GET /"`（方法窄路径宽）
与 `"/mcp/"`（方法宽路径窄）互不包含。所以 dashboard 的根兜底不带方法限定。
这类错误编译不出来、只在启动瞬间炸，`TestMCPEndpointCoexistsWithDashboard` 守住它。

### 5. 单例靠端口绑定，`index` 子命令也争这把锁

两个写者会读到同一个水位、解析同一段追加内容、各写一份块——事务只保证各自原子，
不会互相察觉，结果是同一 `seq` 出现重复块。所以 `serve` 与 `index` 抢同一个端口，
且**在打开索引库之前**就退出。

### 6. 摘要块存在 `seq = -1`

摘要要能被关键词检索命中（R11.2），所以它必须是 `blocks` 里的一行、进 FTS5；
但它不是对话的一部分，不该出现在回读视图里。用负序号同时满足两者：
回读从 `seq >= 0` 翻页，摘要自然被排除。

⚠️ **代价是一条容易漏的不变式：凡是「数消息」的地方都必须带 `seq >= 0`。**
漏掉它的后果不是报错而是错数——`GetSession` 的 `Total` 会比列出的条数多 1，
消息数正好是整页倍数时前端就多出一个点进去空白的「下一页」；
`msg_count` 则会在已摘要会话的下次追加时 +1，而那个数字正是检索结果与
时间线上显示的「N 条消息」。这个 bug 真的发生过，靠 `repairs` 自愈存量数据修回来的。

### 7. 高亮哨兵是控制字符，不是 `<mark>`

片段正文是会话原文，里面完全可能有 `<script>`。后端吐 `U+0002/U+0003`，
前端**先整体 HTML 转义、再**换成 `<mark>`；顺序反了就等于把历史会话里的任意 HTML
注进页面。给 MCP 与聊天 agent 的文本则走 `StripAll` 全部去掉——
实测本地模型会把 `\x02 \x03` 原样抄进给用户看的答案里。

### 8. 四套主题 = 同一组 CSS 变量的四组取值

`theme.css` 里 `[data-theme="desk"|"paper"|"editor"|"term"]` 各定义**同一组** token，
其余样式一律写 `var(--x)`。加一套皮不用碰任何布局代码；反过来，某套主题漏声明一个
token 会被 `TestThemesDefineSameTokens` 当场拦下，而不是在页面上表现为一处怪颜色。

明暗分两层：顶栏按钮切的是 **mode**（亮 / 暗 / 跟随系统，三态循环），设置页选的是
**pick**（亮时用哪套 / 暗时用哪套）。合并成一个「五选一」列表的话，「跟随系统」就
没处安放了。

防闪烁只能靠 `<head>` 里那段内联脚本：外链脚本要等 HTML 解析完才执行，那时备份
已经用默认色画过一帧。它是全站**唯一**允许的内联脚本，`test/e2e/theme_test.go` 断言
「有且仅有一段、在 head 内、样式表之后、body 之前」。

⚠️ 一个踩过的坑：作者样式表里的 `display` 会盖掉备份给 `[hidden]` 的 `display:none`，
于是 `el.hidden = true` 看着毫无反应。`.filters` 和 `.chat-form` 都中过招
（后者意味着「LLM 不可用时聊天入口置灰」实际没生效）。现在 layout.css 顶部有一条
`[hidden] { display: none !important; }` 兜底。

### 9. 配置元信息只声明一次，热生效靠「每次用时取」

`config.Fields()` 是 16 个配置项的唯一声明（key / label / help / kind / hot / min / max /
options），`GET /api/config` 把它下发给前端渲染整张表单——前端不写第二份字段清单，
新增配置项只改 `meta.go`。`TestFieldsCoverEveryConfigKey` 反向校验条数，漏一个就失败。

热生效的关键不在保存那一侧，而在**读取**那一侧：`config.Live` 持 `atomic.Pointer[Config]`，
`summary.Worker` 与 `chat.Agent` 必须每轮从它取值。启动时把 Model 拷成结构体字段的
那一刻，这个配置项就悄悄变成「需重启」了。真正需重启的四项（两个端口、`db_path`、
`scan.roots`）在元信息里标 `hot:false`，界面上打角标并给出重启命令，不假装已生效。

保存只写**与默认值不同的键**：文件里永远只有「你改过的东西」，将来调整默认值能自动
跟随，而不是被一份固化的旧默认值锁死。写入走 `.tmp → chmod 0600 → rename`。

### 10. 路由走查询串，不走路径

URL 是「在看什么」的唯一来源；`localStorage` 只留偏好（明暗、主题指派、左栏两态）。
早先把当前视图存在 localStorage 里，代价是链接分享不出去、后退键直接退出应用、
两个标签页互相覆盖。

选查询串（`?view=digest&id=17&seq=42`）而不是路径（`/session/17`）的理由是实测的：
dashboard 的根处理器是 `http.FileServer`，未知路径返回 **404**，要支持路径式路由
就得在服务端加 SPA 兜底。查询串则服务端一行不动。

两处易错，都有测试守着：

- **`switchView` 与 `mountView` 必须分开**。前者是「用户点了导航」会写历史，后者是
  「按状态渲染」不碰 URL。不分开的话，`popstate` 里调用会再 push 一次，与浏览器
  自己的历史打架。
- **回读是覆盖层不是视图**，所以 URL 里是「底层视图 + id/seq」。这样「关掉回读回哪」
  由 URL 自己表达，不用另存 back 状态。⚠️ 实测踩过：`apply` 里若先挂底层视图再开回读，
  两个异步 fetch 会互相覆盖——检索结果回来得晚就把回读内容顶掉了。所以 URL 带 `id` 时
  根本不挂底层视图的内容。

### 11. Markdown 必须配消毒，这是量出来的

会话内容是敌意输入：里面有抓过的网页、`cat` 过的文件、工具吐出的任意字节。
实测 `marked.parse()` 的裸输出：

```html
<h1>Hi</h1>
<script>alert(1)</script>
<img src=x onerror=alert(2)>
<p><a href="javascript:alert(3)">click</a></p>
<iframe src=//evil></iframe>
```

四种攻击全部原样透传。所以 DOMPurify 不是「加固」，是管线里**不可省的一环**：
`marked.parse → DOMPurify.sanitize → DOM`，URI 白名单收紧到 http/https/mailto。

选型也是量出来的（自己下下来量，不引用聚合站互相矛盾的数字）：marked 38 KB
（markdown-it 121 KB，插件生态这里用不上；snarkdown 2 KB 但不支持表格，而实测
3 482 个 assistant 块有表格）+ DOMPurify 28 KB，合计 69 KB，对比字体 512 KB 可忽略。

**ANSI 只做 SGR，自写 45 行**：实测 673 286 块里只有 1 274 块（0.19%）含转义序列，
这个比例不值得引终端模拟器，也不值得引一个 MPL-2.0 的依赖。其中 1 136 块是
`tool_result`（上色），**140 块是 `user`**——多是 Claude Code 自己的界面文本被一并
存下来，它们走 Markdown 路径，所以在 `CD.md` 入口把 ANSI **剥掉**而不是上色：
上色要先产出 HTML，HTML 再喂给 Markdown 解析器就乱套了。

⚠️ 渲染前后有两条同源纪律：**先转义、再加标记**。`escHit` 如此，`CD.ansi` 如此；
而给已渲染的 HTML 加会话号链接时反过来——**不能对 HTML 串做正则替换**（会打断标签），
必须遍历文本节点。

### 12. 工具调用：一张映射表 + 三种骨架

`tool_use` 占全部内容块的 **39.4%**（274k / 696k），是回读时看得最多的一类。
R3 之前它按序列化 JSON 原样显示——转义引号满地、命令和说明挤一行。

**为什么不是"每个工具一个渲染函数"**：前 15 个工具覆盖 88%，但尾巴很长（各种
MCP 工具，键名各异）。逐个写既写不完，新工具出现时还会留下空白。改为**声明每个
字段是什么角色**（primary / sub / ctx / diff / body / noise），渲染骨架只有三种：

| 骨架 | 覆盖 | 谁 |
|---|---|---|
| 命令型 | 52.1% | `Bash` / `exec_command` / `write_stdin` |
| 文件型 | 23.2% | `Read` / `Write` / `Edit` / `NotebookEdit` |
| 通用键值 | 其余 | 未在映射表里的一切工具 |

未知工具落通用键值表，**不会有"空白"这种状态**。

另有两类正文根本不是 JSON，各走一条分支：`apply_patch`（3.5%）是 patch 文本，
逐行前缀判断着色，不引 diff 库；`exec`（5.3%）是 JS 源码，走代码块，**不做语言
探测**——用"不是 JSON 对象"反推即可，猜语言只会猜错。

两处细节值得记：

- **`$` 提示符用 `::before` 画，不进 DOM 文本**。用真实字符写的话，选中复制会把
  提示符一起带走，粘出去不能执行——而"复制下来重跑"正是回读命令的主要用途。
- **命令的转义天然还原**：命令是从 JSON 字符串解出来的，`\"` 自动变回 `"`，
  不需要手工反转义（手工做反而容易做错）。

⚠️ **判断正文形态必须走 API，不能读裸库。** 最初直接读 SQLite 的 `body` 列，
得出"31% 非法 JSON"的结论，实为读到了 CJK 单字切分用的 `U+0001` 分隔符——
那是索引内部表示，API 下发前会 `Strip`。按 API 输出重测，真实比例是
**91.2% 合法 JSON**。这个坑会再犯，所以写在这里。

### 13. 会话名：回填独立于增量索引

Claude 的 JSONL 里有 `custom-title`（用户 `/rename`）与 `agent-name`（自动生成）。
它们**不是消息**，一直在 `ignorableTypes` 里被跳过——这个归类是对的，
错的是由此推出「所以不该用」。实测只有 82 / 3067（2%）的会话有名字，
但那 82 个恰恰是你手动标记过、因而最想再找到的。

三处设计要点：

**① 标题存在 `Cursor` 而不是 `SessionMeta`**：`Meta()` 只读文件头 50 行，
而标题记录散落全文（同一文件里各出现 274 次，改名会追加新行）。
只有 `Parse()` 逐行走完，顺手记下不用额外读一遍文件。取**最后一次**出现的值。

**② 空标题一律不写**：增量续读时若新追加那段没有标题记录，`cur.Title` 是空串，
写下去会**抹掉**之前存的名字——而「先命名、后继续对话」正是有名字会话的常态。

**③ 回填走独立路径，不改 `decide()`**：`decide()` 里未变化的文件走 `actSkip`，
所以历史会话必须显式回填。但**不去动 `decide()`** 是刻意的——那是增量索引最核心、
最容易出错的逻辑，为一个 2% 覆盖率的字段动它，风险与收益不成比例。
回填只做三件事：只读打开、找两个特征串、`UPDATE sessions.title`；
碰不到 blocks、水位、FTS。实测 3207 个会话 **12.34 秒**，对比全量重建 13 分钟。

幂等靠新增的 `meta` 表（k/v）记水位。它与 `migrations`（结构变更）、`repairs`
（数据自愈）都不同：那两个每次启动都执行，这个是用来**避免**重复执行的。

**标题不进 FTS**（有测试守着）：2% 覆盖率不值得重建 FTS 表与三个触发器，
而这些名字往往就来自首条消息，本来就搜得到。

### 14. 代码着色：三态机 + 只认无歧义的词法（R7 已废弃，见决策 15）

> **这条决策已被推翻，代码已删除。** 保留记录是因为推翻它的理由（决策 15）
> 比决策本身更有价值：它是一个「统计口径错了，结论跟着错了三期」的实例。

R3 与 R4 都排除了「引库做完整语法高亮」（Prism 最小集也要 +15 KB 且要按语言拆包，
而代码块只占 2–5%）。这条判断没变。本期做的是**极轻量着色**：只认注释、字符串、
数字三类，约 90 行零依赖。

**必须用单次扫描的三态机，不能用多条正则依次替换。** 后者必然出错：第二条正则会
命中第一条产出的 HTML——字符串 `"https://x"` 包成 span 之后，注释正则在它内部找到
`//` 并切断已生成的标记。这与「不能对已渲染的 HTML 做正则替换」是同一个坑，
本项目已遇到三次（会话号链接、patch 着色、这里）。

**转义在最内层分段做**，不是先转义整串再扫描——转义会把 `"` 变成 `&quot;`，
长度和字符都变了，扫描位置就对不上。与 `CD.ansi` 同一写法。

**实测砍掉两个误判源，这是「正确性优先于覆盖率」的具体落地：**

| 第一版认的前缀 | 实测误判 | 结果 |
|---|---|---|
| `//` `/* */` | 无 | 保留 |
| `#` | `# 标题`（Markdown）、`#app {}`（CSS）被整行涂成注释 | **砍掉** |
| `--` | `curl --silent --output x.txt` 整条命令后半段被涂成注释 | **砍掉** |

最后一个在本语料里遍地都是。`#` 与 `--` 的含义完全取决于语言，而判断语言正是
本期明确不做的事——无法确定就不着色，不猜。代价是失去 shell/python 注释的着色。

**最重要的不变式是文本无损**：着色只加标记、不增删任何字符，
每条测试都断言着色前后 `textContent` 与原文逐字符相同。

### 15. 语法高亮：推翻决策 14，因为那个统计漏了一半

R7 引入 highlight.js（124 KB，vendored），**删掉了决策 14 那 90 行自制着色**。
翻转不是因为口味变了，而是因为**支撑决策 14 的那个数字是错的**。

R3/R4/R6 三次拒绝引库，理由都是同一句「代码块只占 2–5%」。那个 2–5% 统计的是
**assistant 正文里的 ``` 围栏块**。可这个工具里看得最多的代码根本不在围栏里——
是 `tool_use` 的命令，占全部内容块的 **52.1%**。把它算进来，「引 124 KB 换半数
内容可读」与「引 124 KB 换 2% 内容可读」是两笔完全不同的账。

> 教训不是「当初判断错了」，而是**用一个只覆盖部分场景的统计去支撑一个全局决策**。
> 这个错误自我延续了三期：后两次拒绝直接引用了第一次的结论，没有人回头问那个
> 分母是什么。

三处具体做法：

- **命令块强制按 bash 高亮，不做自动识别。** `highlightAuto` 在短命令上经常认错
  （`ls -la` 被认成别的语言）。已知语言就别猜——这与决策 14「无法确定就不着色」
  同一条纪律，只是现在我们确实知道它是命令。
- **默认配色不引入新色板**，用 `:root:not([data-hl])` 把 `hljs-*` 类映射到既有的
  `--ansi-*` token。于是高亮天然跟随四套界面主题，不需要为它单独验对比度。
  想要官方配色的人在设置页选，才挂对应的 `<link>`——默认状态下页面 **0 个**
  高亮样式表。
- **50 KB 以上的块不高亮**，直接转义输出。高亮是同步的，几百 KB 的 `Write` 内容
  会卡住主线程；而那种块本来就是拿来折叠的。

### 16. mermaid：3.4 MB 的库，只能按需加载

mermaid 有 **3.4 MB** —— 比页面其余全部资产加起来还大一个量级。它不进
`index.html`，第一次点「渲染图表」才动态插 `<script>`。默认显示源码而非图：
mermaid 块在语料里很少，而 `A --> B` 这种源码本身就读得懂。

**渲染器的输出也要消毒。** SVG 过 DOMPurify 的 svg profile——图里的标签文本来自
会话内容，而 mermaid 自己历史上出过 XSS。「这是我们自己的库生成的所以可信」
是错的：可信的是库，不可信的是喂给它的数据。

守这两条的是结构断言而非人：`index.html` 里出现 `mermaid` 即失败。因为一旦谁
顺手把它加进 `<script>`，首屏体积翻十几倍而**功能一切正常**——没有任何报错会
提醒你，这正是需要测试守的那类退化。

### 17. 子代理：库里一直有这条关系，只是没人用

`sessions.parent_uid` R1 就存了。R8 没有加任何表或列，只加了**一个索引**，
把已有的事实用起来。

**近一半的会话是子代理**（1554 / 3207 = 48.5%），而界面上完全看不出来。
搜 `docker` 命中 435 个会话，其中 **154 个是子代理**——它们混在结果里，
既看不出身份也筛不掉。

**默认必须是「全部」，所以过滤用三态字符串而不是布尔。** 布尔只有两态，
表达不了「全部」。而默认隐藏子代理等于默认藏掉一半语料。

**索引只给「取某会话的子代理」用，不给三态过滤用。** `parent_uid != ''` 的
选择率接近 50%，走索引反而更慢，SQLite 会自己选全表扫。这两件事看起来都在用
同一列，代价结构却完全相反。

**一个主会话可以挂 350 个子代理**，所以：列表默认折叠、展开取前 50、容器自己滚，
并且**明说**「共 350 个，这里显示前 50 个」。不说清楚的话，标题上的 350 和眼前的
50 条对不上，会让人以为数据错了。

**总数必须单独查，不能用返回条数**——否则永远显示「共 50 个」，一个看起来完全
合理、因而没人会去核对的错值。

**`agent_label` 不是名字。** 它的取值是 `agent-afffad963a8f89322` 这类随机标识，
1554 个值全不重复。原先三个列表用它判断「是不是子代理」、回读页还把它直接印在
界面上。前者在当前数据里恰好等价（两个方向的反例都是 0）所以看着正常，但那是
**把显示决策挂在一个随机标识上**——哪天某个子代理没有 label，标记就静默消失，
而筛选仍认它是子代理。改用 `is_sub`（直接由 `parent_uid` 推出，正是筛选用的字段）。

**一条 guard 的价值是变异验证逼出来的。** `Parent()` 里有 `c.parent_uid != ''`，
去掉它测试照样绿——因为当前数据里没有 `session_uid` 为空的会话。但 schema 只要求
`session_uid NOT NULL`，**空串完全合法**：一旦某个畸形文件产出空 uid，全部 1653 个
主会话的空 `parent_uid` 会同时 JOIN 到它，集体认下同一个爹，而界面上看不出异常。
> 变异不咬时，先别急着弱化断言、也别急着删代码——先问「这段代码防的是什么，
> 当前数据里那种情形出现了吗」。这次的答案是「防的是真的，只是还没发生」。

### 18. 四种「失败没有信号」的缺陷，以及怎么把它们变成会响的

R7 与 R8 的验收阶段一共撞出 5 个 bug。事后看它们不是五个孤立错误，而是
**四种模式各出现了一次**，共同点是：功能看起来正常、日志干净、测试全绿，
只有结论是错的。

| 类 | 形状 | 为什么难发现 |
|---|---|---|
| **A. 吞错误让守卫静默失效** | 函数里认真区分了错误，调用点一句 `err == nil` / `_ =` 抹平 | 守卫失灵与守卫放行**长得一模一样** |
| **B. 同步读异步配置** | 值由 `/api/config` 异步赋，使用处同步读 | 输了竞速就什么都不做——没有错值，只是"没生效" |
| **C. 断言取样比命题宽** | 匹到自己写的注释 / 锚点对不上 / 定长窗口 | 一条不会失败的断言，看起来和一条守得很好的断言完全一样 |
| **D. 消毒器静默改内容** | 页面结构还在，内容被悄悄删掉 | 「渲染成功」不等于「渲染正确」 |

**类 A 的判据**：一个布尔条件里如果同时压着「结论」和「有没有结论」，就是错的。
体积上限那句 `err == nil && bytes >= max`，`Stats()` 出错时整个条件为假——
与「没超限」完全同义，于是守卫静默关闭、索引继续无限增长。
**「不知道有没有超」和「确认没超」必须是两个值。**

**类 D 的判据**：凡是消毒 / 过滤 / 转换环节，都要问一句「它删掉的东西，
在页面上还看得出来吗」。mermaid 是「图还在字没了」；被剥 `href` 的链接是
「链接还在、点了没反应」。两者都是结构留下、内容消失。

**类 C 最顽固——本项目栽了六次**，其中**三次是断言匹到了我自己写的注释**。
原因很结构性：解释一条规则时，注释里几乎必然要引用那条规则的关键字。
所以写这类断言的默认假设应当是「我的注释会命中我的模式」。
另外三次是定长窗口越界、定长字节窗口在中文注释里不够长（一个字三字节）、
以及锚点 `\n  function ` 对不上 `async function`。
**修法永远是同一条：命题说的是哪一段，就精确取哪一段**——锚规则本体而不是
它的注释，读到闭合括号而不是数字节，比较两个调用的先后而不是"附近有没有"。

### 19. 变异扫描：把「断言是不是摆设」变成例行检查

上面那六次都是**偶然**发现的。`test/mutation/` 把它变成可复跑的检查：每条断言
配一个它本该拦住的变异，注入 → 跑那一条 → 还原，记录咬 / 不咬。

三条硬约束，每条都是栽过之后加的：**注入前确认锚点命中**（找不到要报「注入失败」，
不能报成「断言不咬」）；**`-count=1`**（e2e 在运行时 `go build`，测试缓存不知道
embed 资源变了）；**`finally` 还原**（异常退出也不把变异留在工作区）。
另有一条**哨兵**用例：某个变异**不该**触发某条断言——只验「会咬」是不够的，
一条什么都咬的断言同样没有信息量。

**首轮 28 条里 7 条「不咬」，逐个追下去只有 1 条是断言真的弱，其余 6 条是变异
写错了**——打在断言从来没主张过的地方。这条经验比扫描结果本身更值钱：

> **变异不咬时，先怀疑变异，再怀疑断言。**
> 判据很简单：先读断言到底主张了什么命题，再让变异去违反那个命题。
> 反过来做，就会把一批本来好好的断言改弱，比原来更糟。

不进常规 `go test`：跑一遍要重复构建二十多次，属开发期工具。

### 20. 工具结果的高亮：只在能判出语言时上色，覆盖率是刻意放弃的

R7 给代码加了语法高亮，但只覆盖**工具调用**（命令本身）。**工具结果整类被留在
外面**——而回读时占屏最大的恰恰是它：`tool_result` 占全部内容块的 **38.9%**
（278 744 / 716 602），其中 exec/Bash 类的命令有 **56.1% 是读文件类**
（`cat` / `sed -n` / `nl -ba` / `head` / `tail`），它们的输出就是源码。

**判定只看调用参数，绝不看输出内容。** 结果里除了源码还有大量构建日志、
traceback、`git status`——对它们做自动识别只会乱涂颜色，而**乱涂比不上色更糟**：
它让人以为那些颜色有含义。现成反例：`highlightAuto` 把一段明显的 JavaScript
（`const cmds = await Promise.all([...]`）认成了 **php**。

**判定必须逐段做。** 第一版规则是「命令里有读取关键字 + 命令里有已知扩展名」，
在真实页面上一眼就看出问题：`git status --short | head -5` 含 `head`，
`git diff x.go | head` 连扩展名都齐了——整段 diff 会被涂成 Go 源码。
改为按 `|` `;` `&&` 切段，**只有以读取命令开头的段，它的参数才算数**
（`sed` 还必须带 `-n`，不加就是流编辑不是读取）。

实测 12 000 条真实命令对比两种规则：

| 规则 | 判出条数 |
|---|---|
| 宽松（关键字 + 任意扩展名） | 5 582 |
| **严格（逐段）** | **1 769** |
| 两者判成**不同**语言 | 110 |

抽查那 110 条差异，严格版取的才是真正被读的那个文件——
`sed -n '512,532p' a.tsx; grep -n "X" b.go` 里，宽松版取到了 `grep` 参数上的扩展名。

**覆盖降到约三分之一是刻意的**。这条决策与决策 15（推翻「代码块只占 2–5%」）
方向相反但道理一致：那次是发现分母算小了所以该做，这次是发现分子里混了错的
所以该收——**判断一个功能值不值得做，看的是"对的那部分有多少"，不是"命中了多少"**。

**行号先剥后高亮**：`nl -ba` / `cat -n` 的输出带着行号去做语法分析，从第一个
token 就错。剥离必须**每一行都匹配**才动手——按行独立判断会把普通日志里
偶尔以数字开头的行吃掉数字。行号用 `::before` 画，不进 DOM 文本，
于是整段选中复制出来就是能直接用的源码（与 R4 的 `$` 提示符同一手法）。

**整体高亮后再切行，且用 DOM 切不用字符串切**：逐行高亮会打断跨行的字符串与
注释；而 hljs 的输出里 span 可能跨行，用 `split('\n')` 切会产生不配对的标签，
浏览器补全后颜色会错位。这是本项目第六次守「不对已渲染的 HTML 做字符串操作」。

### 21. 摘要停摆两天：一个 bug 藏在另一个 bug 后面

摘要队列曾**卡死两天而无人发现**。拆开看是三层，每一层单独都不足以解释现象，
而每一层都让上一层更难被看见。

**第一层：入队复活了 failed，队列被一条会话饿死。**

`EnqueueMissing` 的 `NOT EXISTS` 只排除 `pending` / `running`，于是 `failed`
被选中、再被 `ON CONFLICT DO UPDATE` 重置成 `pending` 且 `attempts` 清零 ——
`FailSummary` 那句「重试 3 次后置 failed，不再占着队列」被完全抵消。
那条会话优先级 0，永远排在最前面，其余 92 条排不上。

**第二层：因为复活得太快，`failed` 计数恒为 0，故障对使用者不可见。**

循环周期约 2 分钟。`failed` 状态活不过一轮就被重置，所以 `/api/stats` 永远显示
`failed: 0`，顶栏那行「3157/3250」看起来完全正常。**两天零完成而没有任何信号。**
这是决策 18「失败没有信号」的又一个实例，而且是最隐蔽的一种：
**不是没记录失败，是失败记录被自己的重试逻辑擦掉了。**

**第三层：生成失败本身也有两个叠加的原因。**

修完饥饿后失败照旧，往下追才发现是两件事：

| | 机制 | 表现 |
|---|---|---|
| `num_ctx` 没设 | Ollama 默认 **2048**，与模型能力无关，超出**静默截断** | 截断从 prompt 开头切，最先丢的是任务指令 → 模型答非所问 |
| thinking 没关 | 推理段与回答段**共用** `num_predict` 预算 | 256 全被推理吃光，`response` 空串而 `done_reason=length` |

两个都验过：同一段 8420 字符 prompt，不设 `num_ctx` 时 `prompt_eval_count=2050`
得到跑题回答，设了得到正确摘要；`gemma4:e4b` 在 `think:false` 下 23 token 就给出
35 字的一句话，不关则 256 token 全烧在推理上、回答 0 字。

> **「服务端默认值」是一类特别难查的坑。** `num_ctx=2048` 不在我们的代码里、
> 不在配置文件里、不在日志里，它只存在于 Ollama 的默认值中，却**改变了程序的语义**。
> 排查时看遍自己的代码都找不出问题，因为问题不在自己的代码里——
> 它在「我们没说的那句话」里。凡是把请求交给外部服务的地方，
> **该显式给的参数就显式给**，不要依赖对方的默认值。

> **第二条教训：一个假设被证实，不等于它是唯一的原因。** 我先验证了截断确实存在
> 就以为找到了根因，修完之后现象没变，才逼出 thinking 那一层。

**第四层（这次一并补上）：让它可见。**

新增 `GET /api/summary/progress` 与「生成进度」页——计数、吞吐、预计完成、
时间窗口状态、**失败清单（会话名 + 原因 + 一键重试）**。
这个页面的重点不是好看的进度条，是把失败摊开：**如果它早就存在，这次卡死当天就会被看见。**

顺带加了生成时间窗口（`summary.window`，支持跨零点）。三条降级纪律：
非法值按「不限」跑但**在界面上说出错在哪**；起止相同视为不限而不是零长度窗口；
`InWindow` 报错时仍返回「在窗口内」——**宁可多跑，不要静默停摆**。

### 22. 上下文预算：三个数从未对齐，以及「显存很贵」这个直觉是错的

R11 修好了 `num_ctx`（不设 = 服务端默认 2048 静默截断），但**分段参数与它仍是脱节的**：

| 常量 | 值 | 换算 token（中文约 0.8/字符） |
|---|---|---|
| `MaxInput` | 24 000 字符 | 约 19 000 |
| `ChunkSize` | 8 000 字符 | 约 6 400 |
| `llm.num_ctx` | 8 192 | 8 192 |

`MaxInput` 是窗口的两倍多，**连单段都压着上限**（加系统提示与 256 输出预算）。
三个数分别在三个时期定下，从来没人把它们放在一起看过——
`num_ctx` 甚至在 R11 之前根本不存在。

**修法是让能算的别写死**：`BudgetFor(numCtx)` 一处推导，`Single` 与 `Chunk` 相同
（分段的唯一目的就是让每段能完整进入一次调用，再给分段单独定一个更小的值只会
增加调用次数）。换算取 0.8 token/字符，往「少喂」一侧偏——喂少了摘要略粗，
喂多了被静默截断，后者代价大得多。

**显存实测推翻了我自己上一轮的判断**（`nvidia-smi`，RTX 4070 / 12 GB）：

| 模型 | ctx=8192 | ctx=32768 | ctx=131072 |
|---|---|---|---|
| **gemma4:e4b**（现用） | 4 498 MiB | **4 906 MiB** | 6 537 MiB |
| gemma4:12b-it-qat | 8 207 MiB | 8 640 MiB | 9 956 MiB |

8192 → 32768 **只多 408 MiB**。KV cache 的增量远小于模型权重，
所以「开大上下文很贵」这个直觉在这个量级的模型上不成立，默认值因此提到 32768。

> ⚠️ **Ollama `/api/ps` 自报的 `size_vram` 不可信**：8192 与 131072 下都显示 3.3 GB。
> 判断显存必须看 `nvidia-smi`。

**不换 12b**：同上下文多吃约 3.7 GB，131072 时占 9 956 MiB（12 GB 卡上桌面还要用，
余量只剩 2 GB）；实测慢 1.5–2 倍；摘要质量提升有限，还蹦出繁体中文。

### 23. 「丢中段」与两次断言写错

`Split` 在段数超上限时原本取**前 6 段 + 后 6 段，中间全扔**。实测 62 个会话落在
这一档，最大的一条抽稀后 **210 万字符**——只有约 5% 进了摘要，
且**中间干了什么毫无痕迹**。

改成均分成 12 组、组内按段均摊配额（每段贡献自己的开头，话题通常在段首交代）；
配额低于 120 字符时等距抽取并留 `〔…中间省略…〕` 的痕迹。
真实复验：那条 210 万字符的会话拿到了覆盖全程的摘要
（UI 重构 / 数据一致性 / API 路由清理 / 缺陷定位四件事分布在会话各处），
可见比例从约 5% 提到约 23%。

**这一期两次自我否定，都是测试逼出来的，方向相反：**

1. **实现比命题弱**：第一版「组内取前一半 + 后一半」——那不过是把「丢中段」
   从整体缩小到组内，单测测出 48/60 的位置仍无痕迹。
2. **断言比命题严**：第一版断言要求「每个标记都幸存」——内容是预算几百倍时
   必然要丢东西，那等于要求实现做不到的事。改成「全文每个区段都要有内容进来」。

> 加上此前六次「取样范围比命题宽」，本项目在断言上栽过的所有跟头都是同一句话：
> **断言要精确对着命题，不多不少。** 宽了漏报，严了逼着实现去满足假需求。

同一轮还有第三次：e2e 那条「预算必须由 num_ctx 推导」第一版写成
「函数体里出现 numCtx」——而入口守卫 `if numCtx < minNumCtx` 里也有它，
把计算式换成常量照样通过。变异验证当场戳穿，改成只看**算出预算的那一行**。

### 24. 修了一条路径，不等于修了这个类

R11 发现「没设 `num_ctx` → Ollama 默认 2048 → 静默截断」，修的是摘要走的
`/api/generate`。**隔一天，同一个坑在问答链路上原样重演**：问答走 `/api/chat`
（因为要传 tools），是另一个函数、另一个端点，请求体里一个 `Options` 都没有。

实测（20 416 字符 prompt，`gemma4:12b-it-qat`）：

| | `prompt_eval_count` |
|---|---|
| 不设 options（修之前） | **2051** |
| 设 `num_ctx=32768` | 13 225 |

三个模型的 Modelfile 都没有 `PARAMETER num_ctx`——**不能指望模型自带**。

**对问答的危害大于对摘要**：它累积多轮历史与检索结果（最多 8 轮），
上下文只增不减，而截断从 prompt 头部切，最先丢的正是系统提示与用户的问题。
表现是答非所问，且不报错。

> **为什么当时没想到第二条路径**：修 R11 时我看到的是摘要的故障，
> 顺着那条调用链一路查到 `Generate`，修好、验证、队列恢复——**证据链是闭合的**，
> 没有任何东西提示还有别的地方也在调 LLM。
>
> 教训不是「要更仔细」，而是**修一个类的缺陷时，先去数这个类有几个实例**：
> 「谁在调用外部服务」这个问题，一句 grep 就能回答，而我当时没问。

**修法是抽一处而不是在第二条路径上再写一遍**：`buildOptions` 两条路径共用，
「加一个请求参数」从此只有一个地方可改。断言守的也是这一条——
不是「某处写对了」，而是**不会再有第三条路径自己拼 options**。

### 25. 两个模型在这张卡上不能共存

`nvidia-smi` 实测（RTX 4070 / 12 282 MiB）：

```
只驻留 gemma4:e4b（摘要）      ：5117 MiB
再请求 gemma4:12b-it-qat（问答）：8851 MiB
/api/ps 显示此刻只有 12b —— e4b 已被挤出
```

不是 5117 + 8640 = 13 757，**因为装不下**。于是：一提问就把摘要模型挤掉，
问完再跑摘要又得重新加载，来回抖动。

**代码不处理这件事**：自动降级到小模型会让问答变差且用户不知情，
自动改窗口是替用户做决定。**缓解办法是 R11 的生成时间窗口**——
把摘要设成夜间跑，白天只有问答的模型驻留，两者错开。

模型本来就是分开配的（`summary.model` / `chat.model`），
但 `llm.num_ctx` 是共用的一个：实测 8192→32768 在 e4b 上多 408 MiB、
在 12b 上多 433 MiB，分开设省不下什么，却多一个会再次失配的旋钮
（决策 22 的教训正是三个数各自为政）。

### 26. 给 agent 划的范围必须是代码，不能是提示词

问一问支持按项目限定范围。实现上有一个选择：写进系统提示让模型自觉带上，
还是在工具调用前强制覆盖。**必须是后者**，理由有两层：

**一、模型会忘。** `search_sessions` 的 `project` 参数与 `list_projects` 工具
都存在了两期，实测模型**一次都没主动用过**——它更倾向直接猜关键词。
这是 R13「模型能做不等于模型会做」的又一个实例。

**二、范围错了会被重试机制放大。** agent 首轮没命中会自己改写查询重试（R10 的
核心设计）。范围错了，它就**在错误的范围里反复改写**——用户看到的是
「搜了三轮都没找到」，而东西就在隔壁项目。

实测坐实：范围限定在 chatdex 却问 kgg 的事，模型改写了 3 轮，
**每一轮的 project 都被钉在 chatdex**，一次都没越界。

配套的两个决定：

- **`get_session` 不受范围影响**。它按 id 读取，已经定位到具体会话了，
  再拿范围挡它会让「点开搜索结果」这条路径莫名其妙地失败。
- **事件流发生效后的参数**，不是模型给的。事件流是给用户看「它到底搜了什么」的，
  发一个没真正执行过的检索条件等于展示假象。

**项目清单直接塞进系统提示**（限 20 条），同样是因为不能指望模型去调
`list_projects`；并写明当前范围，否则模型会对「怎么搜不到别的项目」感到困惑。

### 27. 写了门控却等于没等

问一问的范围下拉第一版只有「全部项目」一项。查下来 `CD.projects` 有 131 条、
DOM 元素在文档里、手工照渲染逻辑跑一遍能出 21 项——**代码是对的，就是没被执行到**。

根因在 `CD.boot()` 的顺序：

```js
CD.route.apply(CD.route.read());   // ← 首个视图在这里挂载
loadStats();
CD.projectsReady = loadProjects(); // ← 就绪信号在挂载之后才建立
```

视图挂载时 `CD.projectsReady` 还是 `undefined`，于是
`(CD.projectsReady || Promise.resolve()).then(render)` 的兜底立刻兑现——等于没等。

> 这与决策 18 的「同步读异步数据」是同一类，但**更隐蔽**：
> 我确实写了门控，代码读起来像是处理过了。真正的问题是**门控本身还没就绪**。
> 一句话：**兜底值会把「还没准备好」伪装成「不需要准备」。**

修法是把就绪信号提到挂载视图之前，并加断言守住这个顺序。

### 28. 备份对接 restic，不自研 —— 而 chatdex 只做 restic 做不到的那部分

要给会话做归档时，第一版结论是**自研**：会话文件只追加不改写，做个镜像归档
看起来很简单。两次测量把这个结论翻了过来。

**第一项测量推翻了「只追加」这个前提。** 7 天 8989 轮扫描里，累计触发了
**1811 次「重建」信号**（`size == offset` 但 mtime 变了）。索引层可以粗判——
判错就重解析一遍，浪费 CPU 但结果是对的；归档层不行——**判错一次就留一份
几百 MB 的重复副本**，而且完全看不出来。restic 的内容寻址分块天然免疫这一整类问题。

另外三条：备份是「错了就完蛋」的功能，restic 有生产验证与 `restic check`；
源数据含明文凭证（这也是索引库 0600 的原因），restic 默认加密，自研等于
再造一份长期留存的未加密副本；restic 0.19 是单个静态二进制，装在用户目录即可。

**但对接不等于做壳子。** 分工划在这里：

| | restic | chatdex |
|---|---|---|
| 存得住、存得安全 | ✅ 去重/压缩/加密/校验 | — |
| 知道该存什么 | ❌ 只认路径 | ✅ 配置里的源列表 |
| **存了没有** | ❌ 不知道什么是会话 | ✅ 覆盖率校验 |
| 消失的怎么读回来 | 需要人工 restore | ✅ 界面里直接读 |
| 定时调度 / 保留策略 / restore | ✅ 它自己的活 | ❌ 明确不做 |

**覆盖率校验是这条分工里 chatdex 唯一不可替代的作用**：`restic ls --json`
⨯ `sessions.file_path`，回答一个 restic 永远答不出的问题——「我索引过的那些
会话，备份里到底有没有」。

三分类做完之后真数据又逼出了第四个计数：「未覆盖」这一桶里其实混着两件
天差地别的事——「没备但源还在」（去勾上就好）与「没备且源已没」（永久丢失）。
实测这两个数是 **0 和 183**。只报一个总数，等于把「已经丢了 183 个」说成
「你漏备了 183 个」。`LostTotal` 做成 `Missing` 的**子集**而非第四类，
三类相加仍等于总数。

**两个只有真跑 restic 才会暴露的坑。**

**`snapshots --json` 是时间正序，`find --json` 是倒序**——两个命令方向相反，
且都没有文档保证。按「与 snapshots 同向」取末位，会稳定地拿回**最老**的那个
版本，而它**看起来完全正常**：内容是真的、格式是对的，只是旧了。现在改成
两边顺序都不依赖：拿 `find` 的 ID 去 `Snapshots()` 查真实时间取最大。

**exit code 3 不是失败**，是「部分源数据读不了、其余都备好了」。当成失败的话，
一个权限不足的文件会把整次备份显示成红的，用户据此以为什么都没备。

**从备份读回来，读的到底是什么。**

「让已消失的会话能显示」**不是**理由——索引里已经有完整消息体，`alive=0` 的
会话现在照样能读。真正的理由是索引对工具结果**故意有损**：超 `tool_result_cap`
（默认 4096）截断、非文本清空。实测 706362 个块里 **43637 个被截断**，涉及
2567 个会话。那部分内容只在原件里，而原件一旦被日常清理删掉，就只剩备份这一份。

只读铁律对恢复同样成立：取回**不落盘、不写回源目录**，界面只给出可复制的
`restic restore` 命令。

**实测数字。**

| | |
|---|---|
| 首次全量备份 | 4.22 GB / 7036 文件 → **28 秒**，仓库 1.8 GB（3.4× 压缩） |
| 无变化再备一次 | **767 ms**，零增长 |
| 覆盖率校验 | **1759 ms** / 3265 个会话 |
| `restic dump` 229 MB | **947 ms**，逐字节相同 |
| `restic find --json` | **737 ms** |
| 首次校验结果 | 已覆盖 3082 · 未覆盖 183（**全部是永久丢失**）· 可救回 0 |

最后那一行是这个功能最诚实的一句话：**它来晚了 183 个会话**。
那 183 个在第一次备份之前就消失了，备份救不回已经没的东西，只能从今天起保护。

### 29. 提示词里的每一个字都是模型的素材

摘要提示词上连踩三种形态，都是同一件事：**你写进提示词的东西，模型分不清
是「给你的指令」还是「可以用的材料」。** 以 3157 条真实摘要为样本：

| 形态 | 提示词里写的 | 模型的产出 | 真实语料 | 7b 上 |
|---|---|---|---|---|
| 示范词当词汇 | 「例如应写成『增量备份工具』」 | 把这个词抄进 pprof / FTS5 / certbot 的摘要 | 1 条 | 9% |
| 枚举当格式 | 「概括：做了什么 / 涉及哪个项目 / 结论是什么」 | 「做了压测**/项目** X **结论** Y」，重则整篇带小标题的 Markdown | 2 条 | 常见 |
| 抄原话当摘要 | （没禁止） | 以「好的 / 我已经」开头——助手最后一段回复的前 120 字 | **41 条** | — |

三条对应的改法：

1. **示范规则，不示范词。** 要说「换成品类词」，不要举「TimeMachine → 增量备份工具」。
2. **别写斜杠枚举。** 那读起来就是输出模板。改成散文式描述，并**显式禁止**
   分点 / 小标题 / 加粗。
3. **显式禁止抄原话**，尤其点名「不要把助手最后那段回复当成摘要」——
   很多会话的结尾本来就长得像摘要，模型顺手就抄了。

还有两条工程上的教训：

- **`maxSummaryChars = 120` 的硬截断救了场**：整篇 Markdown 被砍成 120 字，
  难看但没撑爆界面。**约束模型的同时要在代码里兜底**——提示词是请求，不是保证。
- **修提示词只管以后。** 存量得显式清空重生成（摘要是派生数据）。
  注意入队条件是 `summary IS NULL`——设成空串会一条都不触发，我在这上面卡过一次。

同期还发现两条断言互相打架：一条要求提示词里必须出现示例词 `TimeMachine`，
另一条禁止示范词。**加新断言前先搜一遍既有断言。**

### 30. 「跳过」与「通过」在输出上同形

给开源仓补 CI 时，第一版跑出来是绿的。装 restic 那一步的日志明明白白写着
`restic 0.19.1 compiled with go1.26.4`，测试也全过。

但 `internal/backup` 只用了 **0.004 秒**——所有需要真二进制的用例
全部 `t.Skip` 了。

```
ok  	github.com/cygmris/chatdex/internal/backup	0.004s   ← 什么都没测
ok  	github.com/cygmris/chatdex/internal/backup	44.317s  ← 真跑了
```

**这两行除了耗时之外没有任何区别**，而没人会盯着 CI 日志里的耗时看。

根因是一个更普遍的形状：**测试和生产用了两套找同一个东西的办法。**
生产代码走 PATH（`Config.bin()` 不配路径时返回 `"restic"`，交给 exec 查找），
而测试助手 `findRestic` 查的是两个写死的路径——CI 装在 `/usr/local/bin`，
两边都不沾。两套办法只要有一套在某个环境里失效，测试就静默退化成空跑。

> 这一类**变异扫描也抓不到**（决策 19）：变异在本地跑，那里 restic 找得到，
> 断言照常会咬。它只在「另一个环境」里现形——而那正是 CI 存在的理由，
> 却也正是没人逐行读日志的地方。

两条改法，缺一不可：

1. **测试用与生产同一套查找逻辑**（`exec.LookPath`），写死的路径只作兜底。
2. **在 CI 里显式断言「它真的跑了」**——`go test` 没有「跳过即失败」的开关，
   只能自己数：检出 `--- SKIP` 就报错，通过数少于预期也报错。
   已藏掉 restic 验证过这道守卫会咬。

一句话：**只要一个测试可能被跳过，就必须有东西在盯着它到底跳没跳。**
否则「有测试」这件事本身会变成一种错觉。

## 安全约束（不可放宽，逐条有代码与测试）

| 约束 | 实现 | 守住它的测试 |
|---|---|---|
| 只读会话文件 | 一律 `os.Open`（`O_RDONLY`） | E2E：跑完整流程后原始文件 size/mtime/内容逐字节相等 |
| 配置写入路径固定 | 只写 `~/.config/chatdex/config.json`，前端给不了任意路径 | `ConfigStore` 最小接口 + 保存单测（权限 0600、原子写、失败不动原文件） |
| 只监听 `127.0.0.1` | `const loopback`，地址不做成配置项 | 集成测试真的去本机局域网 IP 上连一次，连得上就失败 |
| 索引库 `0600` | `Open` 显式 chmod 主库与 `-wal`/`-shm` | 单测 + E2E 双重断言 |
| LLM 只允许回环 | `llm.ValidateEndpoint`，构造即失败，无开关；**保存路径同样过这一关** | 7 个远端/内网/通配端点的负例 + 设置页保存的 3 条负例 |
| 无向量索引（R8 门控） | 代码里无 embedding 表/列/方法 | `grep -rniE 'embedding\|vector'` 仅命中注释 |
