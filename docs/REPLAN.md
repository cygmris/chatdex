## timeline-reader-navigation（R17，2026-08-18）——长会话不能再让日期过滤与回读落点各说各话

- **触发**：`view=timeline&from=2026-08-18&id=32` 打开后显示 6 月内容，7137 条会话的底栏又只能逐页翻。
- **发现**：`id=32` 实测从 2026-06-20 持续到 2026-08-18；旧 Timeline 只检查 session 起止区间相交，点击又固定传 `seq=0`。范围内真实首条消息其实是 `seq=7089`。
- **踩的坑**：R1 implementation log 曾把「时间线看 session 而非 message」当成选择 session 区间的理由；长达数月且中间有空档的 session 证明这个前提不成立。日期过滤说「有活动」就必须由 `blocks.ts` 证明。
- **验收实测**：真实浏览器从时间线点入后 URL 含 `seq=7089`；第 72 页显示 `7101–7137 / 7137`，刷新保持，999 clamp 到 72；375px 无横向 overflow。当前运行库上 5 次日期 Timeline 请求为 0.411–0.843s。
- **排查外溢**：Timeline 目前静默忽略 `q`／`kind`／`tool`；前端固定 `limit=200`，而后端在 LIMIT 后才累计 `total`。它们是同一份 pagination/filter contract 的独立缺陷，已登记 `timeline-filter-and-pagination-contract`，本轮没有塞进 R17 冒充顺手修完。

## backup-coverage-truth（R16，2026-08-17）——备份页在说谎，而谎话是「一个算术正确的数字」

### 起因是一个问错的问题

用户问「备份是不是漏了 memory 目录」。查下来 **Claude 的 memory 其实备了**
（它挂在 `~/.claude/projects/<项目>/memory/` 下，随会话一起，实测 788 个文件），
真漏的是 **Codex 的 `~/.codex/memories/`**——152 个文件，虽是 git 仓却只有
1 条本地提交、没有远端。

但顺着查下去撞见两件比它更要命的：

1. **覆盖率页拿 7 天前的快照报「已覆盖 3082」。** 那 7 天新建的 664 个会话
   一条没备，却既不在「已覆盖」也不在「未覆盖」——**它们从统计里消失了**。
   加上快照时间后再核对，未覆盖从 183 跳到 **847**。
2. **`after_scan` 默认关着，在真机上一次都没跑过。** 开关是 R15 做的，
   默认给了 `false`，于是备份从配好那天起静默停了。

### 学到的

**一个数字可以算术正确而操作误导**（→ 决策 31）。「已覆盖 3082」没算错，
错在它依赖一个**过期的基准**而不肯说。判据固化下来了：数字若依赖某个基准
（最新快照 / 上次扫描 / 截止时间），必须**同时报出那个基准**——只给结论，
读者只能默认基准是「现在」，而那个默认在出问题的时刻恰恰是错的。

**「表是数据」这条要配一份可检验的排除清单**（→ 决策 32）。只是「不写进
knownPaths」等于口头承诺；维护一份 `knownExcluded`（含理由）并断言两者
不相交，才拦得住将来顺手加一条 `~/.claude/cache`。

**又写了一条假测试。** 阈值判定那条在测试里重算了一遍被测表达式，
无论实现怎么改都绿。根因是判定内联了 `time.Now()`——**不可注入时间的判定
就没法验跨阈值那一侧**，而那一侧才是它存在的理由。

### 计划变更

- 规划时说要备 12 项，设计阶段剔掉了 `memories_1.sqlite`（派生数据 + WAL
  撕裂风险），实际 11 项。**剔除的理由写进了 `knownExcluded` 并有测试守着**，
  而不是默默不写。
- 确认**不需要** restic `--exclude` 支持：顶层凭据文件都在候选子目录之外，
  按子目录建议天然绕开。这条从需求阶段就写死了范围，没有中途扩张。

      **若还出现，说明自动备份有别的失败路径没暴露**（那正是 R15 加

## R18 · view-lifecycle-and-url-scope（2026-08-25）

### 新发现

**用户报的「自动跳到生成进度」根本不是跳转。** URL、`CD.view`、左栏高亮三者
全都没动，动的只有 `#view` 的内容——离开的进度页每 10 秒把当前页面就地覆写。
使用者能观察到的只有「内容变了」，而「跳转」是对这个现象最自然、也最错的解释。
⇒ 可迁移的判据：**「页面跳了」这类报告，先分别量 URL、路由状态、DOM 三者**，
它们不一致的方式本身就指向根因。

**`unmount` 被定义了但从没被调用**——两个视图里写得一丝不苟，`boot.js` 里出现
**0 次**（→ 决策 33）。读代码的人看到 `unmount()` 就认为资源被收了，于是不再
怀疑这条路径。**缺席的不是代码，是调用；而调用的缺席在阅读时完全不可见。**
⇒ 注册型接口（`register({mount, unmount, refresh})`）的每一个成员都要有一条
断言证明它有调用点。

**同一份知识散在三处时，第三处已经悄悄漂移了而没人报过。** URL 参数归属原本
散在 `href()` 全量序列化、筛选条的 `['search','timeline','digest']`、顶栏提交的
`['chat','settings']` 三处。`progress`/`backup` 不在第三份里，于是**在那两页按
回车搜索什么都不会发生**——没有报错、没人报过，是收敛成一张表时才掉出来的。

**「URL 里没有」不等于「值是空」**（→ 决策 34）。修 `href` 只写该视图的参数之后，
`read` 那一侧必须同步：读设置页 URL 时不能把 `q` 置空，否则「切走再切回」会洗掉
筛选。这与 R16 的「陈旧快照冒充已覆盖」、决策 31 是同一族——**缺少信息与信息为空，
在数据结构上同形，在语义上相反。**

**🔴 变异扫描的前提是基线为绿，而运行器不检查这一点。** 加严后的断言按文本搜
`CD.view !== name`，而 `mountView` 的注释里逐字写着这句话——干净代码也红。
「本来就红」与「被变异咬到」在输出上完全同形，于是第一次跑出来的 67/67 毫无意义。
⇒ 本仓注释写得详细、常逐字引用旁边的代码，**对代码做文本断言必须先剥注释**
（`stripJSLineComments`），并配阳性对照防止「剥过头」变成新的假绿。
这是取样范围栽的第 N 次，前几次也是匹到自己的注释。

**一条变异不咬，这次错在断言不在变异。** 按纪律先怀疑变异是对的，但查完要接受
结论可能反过来：收错视图与跳过收尾，在「调用点存在」这个粒度上与正确实现同形，
断言必须验到**收的是哪一个**。

### 计划变更

- 规划时以为是两个独立 bug，排查后确认是同一条纪律的两次缺席（声明了却没人执行的
  契约），因此合并成一个 spec 而不是两个。
- 顶栏搜索在 progress/backup 上静默无效这个缺口，不在用户报的范围内，是收敛归属表
  时掉出来的。**同一根因的第三个表面，顺手一起修**——不是范围扩张，是同一处改动。

### 下一步

- [ ] `timeline-filter-and-pagination-contract`（backlog 里已登记）：timeline 后端
      忽略 `q`/`kind`/`tool`。本期归属表按「前端实际发送」写，等于把这个不一致**显式
      留着**；那条 spec 落地时要回来同步归属表。
- [x] ~~这条边界目前靠人~~ —— 已补 `TestViewsThatAcquireResourcesRegisterUnmount`
      （任务 4）。`TestEveryRegisteredUnmountIsCalled` 只验「定义了的会被调用」，

      就必须注册 `unmount`**。

## R19 · timeline-filter-and-pagination-contract（2026-08-29）

### 新发现

**backlog 里记的规模低估了一个量级。** 原条目写「超过 200 的会话不可达」，
听起来像尾部截断。开工前先量了一遍：**118 个项目只看得到 6 个（95% 不可见）**，
`project-a` 项目头写着 10 个会话而它真的有 182 个。
⇒ 可迁移的判据：**backlog 条目是当时顺手记的印象，动工前必须重新量。**
「记录里说 X」与「现在确实是 X」是两件事——这与「别拿注释当事实」同一族。

**「解析了但没用」是第三种状态，而它在界面上不可见**（→ 决策 35）。
`parseQuery` 完整解析 `q`/`kind`/`tool`，`Timeline` 完整收到，`sessionFilters()`
从不读。使用者选 `kind=summary`：下拉变了、URL 变了、列表重载了、没有报错——
**四个正反馈齐全，结果一条没变**。这样过了一个月没人报过。
⇒ 一个视图对每个它**接受**的参数只能有两种结局：用它，或显式拒绝。

**「哪种 SQL 写法更快」没有一刀切答案**（→ 决策 36）。设计初稿定「一律相关
EXISTS」，依据是一次在 `kind`/`tool` 上的实测（111 ms vs 249 ms）。套到 FTS 上
实测 **515 ms vs 0.37 ms**，方向完全相反——FTS 没有 `session_id` 那一侧的索引，
相关子查询等于对每个候选会话重跑一次全文查询。
⇒ **拿一个谓词量出来的结论，不要当成对所有谓词都成立的规律。**
这与「别拿近 N 天当分布」是同一个错误的两个表面。

**「0.9 ms，不值得优化」这个判断本身是在错误的条件下量的。** `project_total`
原本是单独一条 COUNT 查询，设计里写「实测 0.9 ms」——那是**无筛选**下量的。
带上 `kind=summary` 后，那条查询自己就要 300 ms，而且意味着**昂贵的过滤跑两遍**
（API 613 ms vs 同一条 SQL 287 ms，差正好一倍）。改用 `COUNT(*) OVER ()` 随行下发。
⇒ 量一个「值不值得优化」的开销时，要在**最坏的那个输入**下量，不是最常见的那个。

**文本断言与行为断言各管一半，变异要分开挂。** `TestTimelineUsesEveryParsedQueryField`
守的是「字段没被完全遗忘」；把 `args = append(args, m)` 改成 `_ = m`（读了却不拼进
SQL）它抓不到，也**不该**抓到——抓那种形状的是行为断言。一条变异「不咬」，
查完是挂错了对象，两者本身都对（与 R16 同类）。

**改了函数体也会让别处的变异锚点过期。** 任务 2 把 handler 里的 `gs` 改成 `res`，
一条既有变异因此**注入失败**——等于那条断言当期根本没被验证，而扫描报告里
「注入失败」很容易被当成噪声划过去。

### 计划变更

- 需求 2.4「项目内超过 20 条的会话仍可达」原计划要做展开交互，
  实现到任务 3 时发现**它已经被顺带满足了**：筛选条现在真的生效，缩小范围即可看到。
  于是不做展开交互，也不引入第二套分页（R17 刚给回读页做过一套）。
- `design.md` 在实现中被改过一次（SQL 写法那条），按流程**先改设计再实现**。

### 下一步

- [ ] `kind=summary` / `tool=Bash` 这类命中面广的筛选仍在 300–400 ms。
      现在没有取舍需要做（不加索引的理由是实测够快），但若日后语料翻几倍要复测。
- [ ] R18 留下的那条边界仍在：新视图**注册**了 `unmount` 与否靠人——
      已由 `TestViewsThatAcquireResourcesRegisterUnmount` 覆盖到「起了定时器/订阅」
      这一类，换一种没被列进正则的 API 仍然认不出。

## R20 · coverage-across-all-snapshots（2026-08-29）

### 新发现

**一条挂了 24 天的「等条件满足」，等的是一件不可能的事。** I5 的验收条件是
「等 `rescued_total > 0`」。复核这个阻塞条件时才发现：`Coverage` 只跟**最新一个
快照**比，而源已消失的会话按定义不在最新快照里 —— 那个数**在结构上恒为 0**。
⇒ 可迁移的判据：**挂起项的阻塞条件也会过期，甚至从一开始就是错的。**
重启一个挂起项时，先验它的**阻塞条件本身**还成不成立，而不是直接看条件满足没有。
这与「backlog 条目是当时的印象，动工前重新量」是同一条纪律往前一步。

**同一个页面，R16 刚修过，又以新形式说谎**（→ 决策 37）。R16 加 `LostTotal` 正是
为了区分「你漏备了 183 个」与「已经永久丢失 183 个」，而 `LostTotal` 本身是错的：
实测 1973 个「永久丢失」里随机 29 个样本有 **25 个（86%）**在旧快照里找得到，
改成跨快照后 `rescued_total` 从 0 变成 **1639**。
⇒ **修完一个「数字骗人」的 bug，不代表那一族在这个页面上绝迹了。**
同族的判据是「这个数的**范围**交代了吗」——R16 交代的是时间范围（快照多旧），
本期漏的是搜索范围（查了几个快照）。

**「没找到」在搜索范围不完整时不构成结论。** 首次建索引 9.4 分钟，期间
「没找到」只意味着「还没在已扫的那部分里找到」。所以 `SeenReady=false` 时
`LostTotal` **扣住不给**，界面显示进度。给进度，不给结论。

**只扫 4 / 567 个快照就已经拿到 1639。** 消失的会话集中在早期快照里，
不必等索引扫完就已大幅改善。
⇒ 一次性成本高的索引，**先让它可用再让它完整**，比「建完才敢用」实用得多。

**变异清单会被自己的重构悄悄弄废。** 本会话第二次撞到：改了函数体形状，
另一条既有变异的 `find` 锚点过期 → 报「注入失败」。那三个字看起来像噪声，
含义却是**那条断言这一轮根本没被验证过**。
⇒ 每轮变异扫描后，「注入失败」要和「不咬」同等对待，不许划过去。

**「不咬」也可能是变异打错了位置。** 「删掉 `if done[sp.ID] { continue }`」没咬住，
查出来 `Scan` 有两道守卫，删一道另一道照样拦住 —— 行为没变，测试当然绿。
变异必须打在**真正的源头**（不读「已扫集合」）上。

### 计划变更

- 本轮本来是要做 I4/I6/I3，复核 I5 阻塞条件时撞出这个 P1，插到最前面做。
- I5 不再是「等条件」，本轮直接验完并 `shipped(R20)`。

- [ ] I4：活着的会话展开被截断的工具结果（2567 个会话有截断，其中 2416 个源文件还在）
- [ ] I6：摘要「不超过 60 字」实测 42% 超标，先判这条要求本身现不现实

## R22 · read-original-for-live-sessions（2026-08-29）

### 新发现

**backlog 条目里的两处描述都不准**——本会话第四次撞到同类：
① 「有 file_path + offset」：`blocks` 表**没有 offset**，只有 `seq`（好在不需要，

## R24 · offsite-mirror（2026-09-01）

### 新发现

**「在别处还有一份」如果不报告它有多旧，等于没有这份**（→ 决策 41）。
异地副本一度靠脚本跑 rclone，chatdex 不知道它跑没跑。2026-08-29 实测落后
1218 个文件 / 约 1 GB，而备份页全程正常——它报的是本地仓，而本地仓确实是好的。
⇒ 副本的价值等于「它在你需要时是新的」的把握，那个把握只能来自持续报告的差额。

**同一族的「同形」又出现两次，都在这个功能里**：
①「没配异地副本」与「配了且最新」的 `behind` 都是 0；
②「连不上异地仓」也是 0。三者含义天差地别，靠 `Configured` 与 `Err` 才分得开。
⇒ 这已经是决策 30/33/35/37/41 的第五次同族出现。**凡是「0 / 空 / 没有」的输出，
先问它有几种成因**，有两种以上就必须有第二个字段去区分。

**「完成」的判据要落在验证上，不是命令的退出码。** `rclone copy` 退 0 只说明命令
没报错。本期把 `rclone check` 逐文件校验写进完成条件，真机首跑 `checked=2903`。

**改配置不重载就下结论。** 验三态时直接改 config.json、`sleep 2` 查接口，两态都没
生效——`live.Get()` 只在 `PUT /api/config` 时重载。数字没变才引起怀疑；否则就会把
「没测到」当成「测过了」写进验收。
⇒ **验一个由配置驱动的行为时，先确认那次配置改动真的到达了运行中的进程。**

**旧东西退役要留碑，不能直接删。** 旧脚本被 RESTORE.md、项目 memory 与肌肉记忆
引用。删掉的话下次照旧路径跑只会得到「command not found」，那句话不告诉人替代品
在哪。改成退出码 1 并打印替代路径。

**两处独立写的代码埋了同一个假设，且不会同时以同样方式暴露。** 加 `backup.mirror`

## R25 grok-updates-transcript — 一句写错的注释，藏掉了 85% 的 Grok 对话

### 发现

**缺陷不在代码里，在一句注释里。** R23 的 `grok.go:44` 写着「updates.jsonl 与
rewind_points.jsonl 是编辑器状态与回滚点，不是对话内容」。那句话是错的，
而正是它让 R23 排除了唯一完整的那份记录，转而索引会被 Grok CLI **原地压缩**的
`chat_history.jsonl`。压缩发生时，扫描器看到 `size < offset` 判为截断并重建
——行为完全正确，结果是原文静默蒸发。

实测缺口用**外部地面真值**量出来（`prompt_history.jsonl` 逐条记录使用者敲过的
提问，不受压缩影响）：1279 条提问里 `chat_history` 只剩 196 条（**15%**），
1054 条（82%）只存在于 `updates.jsonl`。改用后可检索率 **99.8%**。

⇒ 与铁律 1「注释是断言不是事实」是同一条，但方向更狠：那句注释不只是过期，
它**当时就是错的**，且它的错误形态是「排除了一个数据源」——一旦排除，
后续所有测量都在被裁剪过的样本上做，**没有任何机制会让它暴露**。

### 三个把设计推到唯一解的实测

1. **每行都有 `timestamp`**（64722/64722）⇒ 整套时间插值（`readGrokEvents` /
   `fillGrokTimes` / `spread`）变成孤儿，删掉；Grok 从此有真时间戳。
2. **最大文件 264 MB，过滤截断后仍有 51.8 MB / 38421 块**（规划时按 3.1% 正文
   比例估的是 0.7 MB，**差 74 倍**）⇒ 一次性收进内存的老做法不可接受。
   而上一条恰好已经把 `pending` 缓冲区的存在理由拆掉了——**两个问题一个改动**。
3. **`tool_call_update` 独占 87% 的字节**，正文只占 1.5%（加 reasoning 3.1%）
   ⇒ 读 1 GB、索引 30 MB，代价可接受。

### 三处「查找方法自己坏了」

这一轮踩了三次同一个坑，形态各不相同，值得单独记：

| 形态 | 表现 | 真相 |
|---|---|---|
| **验收脚本比错了东西** | 覆盖率 52.6%，看起来像解析缺陷 | `chat_history` 存的是带注入块的**包装形态**（`<user_query>` / `Stop hook feedback:`），`updates.jsonl` 存的是使用者真正敲的那句。剥掉后 74.6% |
| **子串探针必然失配** | 583 条被判成「两处都没有」 | 探针把 `\ " 换行` 换成空格后去原始 JSON 里找子串。改成**按解析器的规则重建再比**，真实遗漏只有 3 条 |
| **变异不咬 ≠ 测试弱** | 去掉 `msg_count = 0` 谓词无测试变红 | **是设计错了**：同一个 `repairs` 里的 msg_count 自愈跑在它之前，会把中间态的 msg_count 重算回真实块数，于是那条谓词在**它唯一该命中的场景里恰好不命中** |

⇒ 第三条尤其反直觉：惯例是「变异不咬先怀疑取样」，这次相反——取样是对的，
**被变异掉的那行本来就该被变异掉**。
